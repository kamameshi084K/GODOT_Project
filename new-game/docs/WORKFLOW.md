# 開発の進め方

1. **仕様整理（Sol）**：`AGENTS.md` と `PROJECT.md` を優先して読み、ユーザーの説明から確定仕様、未決事項、最初に作る範囲、完了条件を整理する。ゲーム性・主要設計が変わる不明点は確認する。通常の実装細部は合理的に判断し、判断と結果を必要な範囲で記録する。
2. **必要な調査**：メインで足りればそのまま進める。独立した仕事を渡す価値がある場合だけgodot_scoutを起動する。毎回2体を使う義務はない。Godotの対象バージョン、必要な公式仕様、依存関係、テスト観点を絞る。
3. **実装・検証（Sol）**：メインだけがコード・テスト・設定・文書を編集する。変更に応じた構文、参照、挙動、回帰を確認する。ゲーム実装後は利用できるGodotで対象機能を確認し、実行できない検証は理由と次の確認方法を残す。
4. **必要なレビュー（Luna）**：変更がまとまってからgodot_reviewerに対象ファイル・変更内容・仕様・完了条件・検証結果を渡す。具体的な不具合や仕様不一致を確認する。小さく明らかな変更はメインの確認で完了できる。
5. **修正・コミット・完了（Sol）**：指摘を判断して修正する。再レビュー・再テストは変更箇所と影響範囲を中心に行う。`PROJECT.md` の現在地と `WORK_LOG.md` の結果・検証・未解決事項を更新する。下記のGit手順で依頼に対応する変更だけをローカルCommitし、コミット内容を確認して完了条件に対する結果を報告する。

## 並列化と引き継ぎ

- 同時に編集する担当はメイン1体。サブはgodot_scoutとgodot_reviewerの最大2体、メイン込み最大3体。サブからの追加起動は禁止する。
- 並列化は「Solの実装とLunaの独立した調査」のように相互に結果待ちしない仕事に限る。調査結果が設計を左右する部分は結果を待ってから実装する。
- レビュー中は対象ファイルを変更しない。並行作業はレビュー対象やその前提に影響しない範囲に限る。レビュー終了後に修正する。
- サブへの依頼は「目的・対象範囲・必要な仕様・期待する出力」を中心にし、可能なら会話履歴全体を渡さない。報告は原則5項目程度で結論・根拠・未確認事項を短く返す。
- 検索と必要箇所の読み取りを優先する。メインはサブの結果を判断に使い、理由なく同じ調査をやり直さない。
- 全文ログ、長い作業記録、全ファイルを毎回読み込まない。引き継ぎは `AGENTS.md` と `PROJECT.md` を優先し、他は必要箇所だけ読む。
- 外部レビューCLI、専用プロファイラ、GitHub操作担当、常設の追加エージェントは構成に含めない。

## Gitと記録

ユーザーが明示的に依頼した実装・修正・設定変更は、Solのメインが必要な検証・修正・ローカルCommitまで担当する。通常のCommit前に毎回追加確認しない。会話の返信ごとではなく、意味のある作業が完了した単位でコミットする。変更がなければコミットは不要。

1. 開始時に作業ディレクトリ、Gitルート、ブランチ、サブモジュールかどうか、未コミット変更とステージ済み差分を確認する。親GODOT_ProjectのGit管理・共通履歴を利用し、作業範囲外の設定・既存ゲームは編集しない。
2. このゲームの今回の依頼に必要な変更だけを特定する。他作業のステージ済み変更は保持し、コミットへ含めたり勝手にステージ解除したりしない。同一ファイルに既存変更がある場合も今回の差分と区別する。
3. 必要な検証・修正後、コミット対象のファイル一覧と差分を確認する。対象パス限定のコミットや一時インデックスなど、既存のステージ内容を保持できる方法を状況に合わせて使う。対象パス全体をコミットする方法は、そのファイルに無関係な差分がないと確認できた場合だけ使う。確実に分離できなければコミットを保留し、対象と具体的な理由を報告する。
4. 日本語のSummaryと短いDescriptionをコミットメッセージの件名・本文にする。作業詳細と検証結果は `WORK_LOG.md` に簡潔に記録し、コミット後はそのコミットの変更ファイルと内容、および残った未コミット・ステージ済み変更を確認する。
5. 完了報告にリポジトリ・ブランチ・コミットID・Summary・短いDescription・検証結果・残存変更・Push未実行を含める。実行できなかった操作は成功と区別する。

Pushはユーザーが手動で行う。CodexはPush・Publish・PR作成を実行しない。リポジトリ分割、`git init`、サブモジュール追加、フォルダ移動、ブランチ切替、既存コミットの書き換えは行わない。Lunaは引き続き読み取り専用で、コミットを含むGit変更操作を行わない。

## 新しいチャットでの確認

Codexのプロジェクト追加でこの `new-game` フォルダを既存フォルダとして登録し、そのプロジェクトの新しいローカルチャットを開く。作業ディレクトリがこのフォルダであること、AGENTS.mdの参照、メインの実効モデルと推論強度を確認する。指定値でなければ黙って代替せず状況を報告する。

カスタム役割が認識される場合、godot_scoutだけに「PROJECT.mdの現在の段階を読み取り、編集せず1行で報告」を一度依頼し、実際のモデル・推論強度・役割認識を確認する。確認後に終了し、常駐させない。設定を読めない場合は信頼状態や上位の管理設定を確認し、承認・権限を弱めて回避しない。確認結果を記録してから、ユーザーのゲーム内容に基づく仕様整理へ進む。
