# new-game の必須事項

- 起動時は本書と `docs/PROJECT.md` を読み、必要な箇所だけ `docs/WORKFLOW.md` と `docs/WORK_LOG.md` を参照する。
- 作業・書き込みはこのゲームのフォルダ内に限定する。親の設定・既存ゲーム・既存のGit変更を変更しない。
- メインは **gpt-6-sol / medium**。仕様整理、設計、分解、実装、検証、修正、統合、文書更新、ローカルCommitを兼任し、コード・テスト・設定を含む全ファイルの編集担当はメイン1体だけとする。別のメインやSol実装担当を起動しない。
- 必要時だけ **godot_scout**（調査）と **godot_reviewer**（レビュー）を使う。両方 **gpt-6-luna / medium**、読み取り専用。サブは最大2体、メインを含め最大3体。サブからの追加起動は禁止する。
- 小さな修正はメインだけで進める。並列化、依頼の最小化、レビュー対象の固定は `docs/WORKFLOW.md` に従う。
- ゲーム内容はユーザーからの説明待ち。説明後に仕様、最初の実装範囲、完了条件を整理する。ゲーム性・主要設計に影響する不明点は確認し、通常の実装細部は合理的に判断する。現段階では2D/3D、言語、ルール、描画方式を決めず、`project.godot`・コード・シーン・素材を作らない。
- 変更に応じた構文・参照・挙動・回帰を検証し、確認済みと未確認を区別して報告する。実装開始後は利用可能なGodotと対象機能に応じて検証する。準備段階ではゲーム起動を要求しない。
- 親のGit管理・共通履歴を継続する。`git init`、サブモジュール追加、リポジトリ分割、フォルダ移動、ブランチ切替、既存コミットの書き換えは行わない。
- ユーザーが明示的に依頼した実装・修正・設定変更には、必要な検証・修正後のローカルCommitまでを含む。通常のCommit前に毎回確認しない。返信ごとではなく意味のある作業の完了単位でコミットし、変更がなければ不要。対象を確実に分離できなければコミットを保留して具体的な理由を報告する。
- コミット対象はこのゲームの今回の依頼に必要な変更だけ。他のゲーム・無関係な変更・他作業のステージ済み変更を含めず、勝手にステージ解除しない。同一ファイルの既存変更も区別する。開始時のGit状態、コミット前の対象差分、コミット後の変更ファイルと内容を確認する。手順は `docs/WORKFLOW.md` を参照。
- Pushはユーザーが手動で行う。CodexはPush・Publish・PR作成を実行しない。
- コミットメッセージはGitHub Desktopでも確認できる日本語のSummaryと短いDescriptionにする。作業詳細と検証結果は `docs/WORK_LOG.md` に短く記録し、会話全文・生ログは残さない。
- 既存の権限・承認設定を継承する。モデルが利用できなければ報告し、無断で代替しない。子フォルダの設定を親の既存チャットへ適用済みとみなさない。
